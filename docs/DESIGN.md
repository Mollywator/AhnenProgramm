# How it works, and why

This is the long half of the documentation: what every part of the program
does and which decision it is the result of. The short half — what the program
is, how to start it, how to point it at your own report — is in
[`README.md`](../README.md).

It is written to be read by whoever picks the program up next, including an AI
assistant. Rules for working here are in [`CLAUDE.md`](../CLAUDE.md); the one
that outranks the rest is that no family data and no real name ever enters this
repository, examples in comments included.

---

## What it does

The source is `source/Genialogie Stammbuch 2023-11-12.pdf`, a 132 page report
generated by *The Complete Genealogy Reporter* out of MyHeritage Family Tree
Builder. It covers 326 people between 1600 and 2023 and carries 96 portraits.

The pipeline reads that PDF, rebuilds the family graph from it, checks the
result against itself, and writes the page.

| Step | Script | In | Out |
|---|---|---|---|
| 1 | `tools/extract_pdf.py` | the PDF | `data/raw/lines.json`, `data/raw/marked.txt`, `data/photos/*.jpg` |
| 2 | `tools/build_data.py` | `data/raw` | `data/tree.json`, `data/validation-report.txt` |
| 3 | `tools/build_site.py` | `data` | `Stammbaum.html` |

`build.cmd` runs all three.  Editing is a fourth, separate path — see
*Editing* below; the two must not be mixed up, and the code is built so that
they cannot destroy each other.

Step 3 refuses to write the page if its script does not parse - it hands the
inline script to `node --check` first, and skips that check with a note when
node is not installed. The data and all 95 portraits are injected into one big
inline script, so a single mangled character kills the entire page while the
file still looks perfectly normal on disk: 2.4 MB, right person count, and a
diagram that never appears. That happened once and cost a round of guessing.

Requires Python 3.10+ with `pymupdf` and `pillow`:

```
pip install pymupdf pillow
```

## Why it is built this way

Every person in the report carries a stable id, printed as a superscript behind
the name. Plain text extraction glues that number onto the name
(`Bertram Ahrenholt12`), which makes the prose ambiguous, so step 1 keeps the
superscripts as explicit `{12}` markers. Everything downstream depends on that.

Facts are taken from whichever part of the report states them most plainly:

- **parents** from each person's own sentence, `als Sohn von X{1} und Y{2}`
- **children** by inverting those parent links, then cross-checked against the
  child lists the report prints under each marriage
- **couples** from shared children, from the event register and from the prose
- **dates and places** from the event register and the place register, which
  are already one fact per line; the prose fills in causes of death and places
  the registers omit
- **names** from the way other entries refer to a person, because those spell
  the name normally while the entry headings are set in capitals

Each person also keeps their full narrative paragraph verbatim, shown in the
page under *Originaltext aus dem Bericht*, so nothing the parser misses is lost
to the reader.

## The validation report

`data/validation-report.txt` — also reachable from the page itself through the
*Prüfbericht* button — lists everything that does not add up. It is not a list
of parser bugs: at the time of writing all 15 entries are inconsistencies in the
source data.

Every person a finding names carries their entry number (`#12`), and the number
opens their sheet (`linkIds`). A finding that suspects two entries of being one
person - "dieselbe Person", "doppelt erfasst", "gleicher Name und Jahrgang" -
also gets *Beide im Stammbaum zeigen* (`pairOf`, `showPair`). It marks both boxes
in the tree exactly as it stands - no new centre, no other view, no zoom - because
two boxes pulled next to each other would claim something the tree does not. A
marked box outside the picture gets an arrow at the edge (`updateSpotArrows`,
redrawn from `paint`); clicking it only pans there. A box the current view does
not draw is named in the bar under the tree, with *Ganzen Baum zeigen* as an
explicit click.

### Merging two entries

`zusammenfuehren.py` merges two records of one person, only ever by hand: from a
duplicate finding, from the bar under the tree, or from a person's sheet
(*Zusammenführen …*, search by number or name). The page shows both records
field by field (`renderMerge`, field list sent by the server). Equal values and
values present on one side are taken; lists are unioned; every disagreement has
to be answered, and a text may be kept from both sides. The merge takes a second
click. Relatives pointing at the removed number are re-pointed, documents move
into the kept number's folder. Merging a parent with its child, or removing a
number that is linked to another tree, is refused.

Each merge is written to `papierkorb.json` beside the tree with both records as
they were, the trail on every relative and the moved files, and kept for 60
days. The Prüfbericht lists it under *Zusammengeführt* with what happened to
every field, and *rückgängig* takes it back: unchanged relatives return exactly,
changed ones only get the link back, and a number handed out in the meantime is
replaced by a new one.

In the editor such a pair can be confirmed as two different people (two uncles
of the same name and year do exist): *Passt so – zwei verschiedene Personen*.
Every decision in the report takes two clicks (`askButton`) so nothing is
clicked away in passing. Confirmed findings - pairs and deaths marked
*Geprüft* - leave the open list for a *Geprüft* section at the foot of the
report, each with its date and *rückgängig*. Pairs are stored under `doppelt`
in `pruefung.json` with a fingerprint of both people's name, birth and parents;
when one of those changes, the finding asks again.

In the editor the same button also carries a check that runs in the background
while the program is open: a mother who died before a child's birth, or a father
who died more than eleven months before it (`diedBeforeChild` in the page,
`died_before_child` in `build_data.py`, one rule tested against one table). It
announces only findings it has not reported before, shows the open count as a
red number on the button, and lets each finding be marked *geprüft* or
*nicht nachprüfbar*. What it looked at and what was decided lives in
`pruefung.json` beside `baum.json` (`tools/pruefung.py`) — never in the tree
file, so the check changes no family data and needs no format version.

The strongest check works like this. The report prints a relationship label
behind every name, always relative to the one person the report was written
for ("Jans 3 x Ur-Großvater").
Those labels are an independent statement about the shape of the tree, so
`tools/kinship.py` recomputes them from the extracted parent links and compares.
216 of the 326 labels are checkable that way, twelve generations deep, and all
of them agree.

The remaining findings are worth a look:

- **One man is in the tree twice** (#143 and #145), both records married
  to the same woman, #144. His parents, his children and their children are
  duplicated along with him. That is why some people show up as both
  *Urgroßvater* and *Urgroßonkel durch Heirat*.
- Two mothers who died before a child of theirs was born (#216, #219).
- A marriage at thirteen (#188), which the report itself states.

## The page

`Stammbaum.html` holds the data and the portraits inline. It has no build step
of its own and needs no server. The window never scrolls as a whole — only the
register and the diagram do.

**The same page in the editor carries addresses instead of portraits.** It is
the one difference between the copy handed to the family and the copy the
program serves, and `build_site.page_html(..., als_adressen=True)` is the whole
of it. The family's copy must carry every picture inside it because it runs from
`file://` with nothing behind it; the editor has a server that can simply say
where a picture is, and `/foto/<name>` hands over the stored file untouched.

What that buys, measured on a tree of 341 people with 96 portraits: building the
page went from 792 ms to 26 ms, and the page from 2,6 MB to 0,77 MB. The page
therefore appears before the pictures do, and the browser fetches each portrait
as it comes into view — `loading="lazy"` was in the template all along and could
never do anything, because a picture already inside the document has nothing to
load. It also shows the portrait at the size it was stored in: portraits used to
be scaled down twice, once in the browser on the way in and again on the way out.

The one thing this costs is that a drawing which **leaves** the window has to be
given its pictures back. An SVG in the Downloads folder, and the same SVG handed
to a canvas to become a PNG, resolve nothing, so every portrait would be an empty
frame. `photosAsData` fetches them at the moment of export, for the people in the
picture only — 29 ms for eighteen of them.

- The register on the left searches names, places, years and occupations.
- Clicking a row opens that person's sheet; clicking a box in the diagram makes
  that person the new centre. The ⓘ badge on a box opens the sheet instead.
- Every other person is then labelled with their relationship *to that centre* —
  computed from the graph, not read from the report. The person sheet also shows
  the path, step by step, from the centre to that person.
- Each box carries the name, the relationship to the centre, and the dates -
  `✶ born` on one line and `† died` on the next. Side by side they fitted only
  while both dates were short, and the one that got cut was always the death,
  so the box is four lines tall rather than three. Portraits of the dead are
  shown in black and white; someone counts as dead when the report says so,
  or once they would be over 110.
- The name in the box is built from the parts - `Vorname Nachname`, and behind
  a comma the Geburtsname where there is one. The sheet writes that line along
  while the name fields are typed in, with a tick box for the birth name that
  starts ticked; anybody who types the line themselves keeps it, and emptying
  the field hands it back to the program.
- Three kinds of people, told apart by fill, border and left edge:
  **blutsverwandt** (solid, coloured edge — blue up the line, red sideways,
  rose down), **angeheiratet** (dashed, warm fill) and **deren Familie**
  (dotted, cool fill) — the in-law's own relatives, who are related to the
  centre through nobody. Clicking an entry in the legend highlights only that
  group and dims the rest, which is the quickest way to read the big views.
- A doubled horizontal line is a marriage, a single line a descent. The sibling
  bar hangs directly under the parents rather than halfway down, so it can never
  be misread as a bracket around a couple, and neighbouring families are
  staggered so their bars do not share a line.
- Two drawing styles: **Tafel** treats everyone alike, like a printed chart.
  **Sippen** additionally draws every married-in family as its own tinted island
  labelled *Familie Hemken · über Cordula*, so it is obvious that the connection
  runs through one marriage and not through a second set of parents.
- Four scopes: *Nahe Familie* (three generations around the centre plus the
  centre's nephews and nieces and parents-in-law; the ▾ menu beside it
  switches those off and grandparents-in-law, siblings-in-law and the
  partner's nephews and nieces on), *Ahnentafel* (see below),
  *Ganze Linie* (every blood relative of the centre plus their partners) and
  *Alle* (all 326). The big views run to roughly 23000 × 1900 pixels, so the
  diagram pans freely by dragging and zooms from 4 % to 400 %; below 62 % the
  boxes drop their portraits, below 30 % they become plain blocks for an
  overview. *Einpassen* fits the whole tree, *100 %* returns to full size.
- **The zoom is a layout change, not a `transform: scale()`.** This is the one
  thing in the page most likely to be "tidied up" into a bug again, so: a
  transform does not re-draw anything. The browser renders the diagram once and
  then stretches that picture, so type and portraits are soft at every zoom
  except the one they were drawn at, and sharpen only while something forces a
  repaint - which is why hovering a box used to sharpen it for exactly as long
  as the mouse stayed there. The zoom therefore runs through CSS `zoom` on
  `#plane`, which is a layout property: the boxes are laid out and the glyphs
  drawn at their true size. `#pan` around it carries the panning translate and
  nothing else, so dragging never stretches anything either.

  There is deliberately no "stretch now, lay out later" step. An earlier attempt
  kept a transform for the length of a wheel gesture and baked it 160 ms after
  the gesture stopped; that leaves a soft picture on screen for as long as
  somebody keeps zooming, which is exactly when they are looking closely.
  Laying out all 326 boxes per wheel notch is too fast to measure - twelve
  zoom steps in the *Alle* view came in under the timer's resolution - so there
  is nothing to buy by deferring it. `paint()` also runs synchronously rather
  than out of `requestAnimationFrame`: where those callbacks are throttled the
  view would otherwise freeze at whatever it last drew.

  Whether the browser really lays out at a given `zoom` is settled by measuring
  a probe element, not by `CSS.supports("zoom", "2")`, which has answered
  wrongly for this property. The footer names the method in use - *Zoom:
  Neusatz* when the diagram is laid out, a warning when the browser can only
  scale a picture - so a report of "it looks soft" can be told apart from "this
  browser cannot do it" without opening any developer tools.

  **Nothing inside the diagram may use `opacity`, `filter` or `mix-blend-mode`.**
  Each of those draws the element into a buffer of its own before blending it
  in, and inside a zoomed diagram that buffer is not allocated at the zoomed
  resolution - so the element renders soft. This is what made hovering look
  broken: `.plane.focus .box:not(.kin) { opacity: .45 }` dimmed every other box,
  and every dimmed box turned soft the moment the mouse touched one, while the
  box under the cursor stayed sharp. Dimming is therefore painted rather than
  blended: a translucent sheet in `::after` over the box, `--veil` and
  `--veil-strong`, plus a dimmer stroke colour for the wires. The full-screen
  grain overlay went for the same reason. The one deliberate exception is the
  `grayscale` on a dead person's portrait, which is small and confined to the
  image.

  Two consequences to keep in mind. `offsetLeft` and `offsetTop` are measured
  inside the zoomed plane, so code that needs plain layout numbers reads the
  inline `style.left` / `style.top` the diagram was built with - `centreView`
  does. And anything that promotes the plane to its own compositor layer -
  `will-change: transform`, `translateZ(0)`, `backface-visibility`, or a blended
  full-screen overlay above it - brings the softness straight back; the grain
  overlay lost its `mix-blend-mode` for that reason, and no `will-change` is set
  anywhere any more.

  Verified at 0.35x, 0.7x, 1x, 1.4x, 1.9x, 2.6x, 3x and 4x: no stretched state
  in any of the eight, box geometry within 0.01 px of the prediction, widths
  exactly `208 * zoom`, 42 of 42 click targets hitting the right person, and all
  eight view/design combinations free of NaN coordinates.
- The relationship rules live twice: in `tools/kinship.py` for the check and in
  the page's own JavaScript for arbitrary centres. Keep the two in step.
- The manual carries a **Technik** section that reads back what the page is
  actually doing: the build stamp with a time, whether the zoom is laying out or
  merely scaling a picture, the zoom in force, and how many elements are being
  drawn through a buffer of their own - which must be zero. It exists because
  "it still looks soft" and "you are looking at yesterday's copy of the file"
  are indistinguishable from a description, and one screenshot of that panel
  settles it. The *Diagramm neu zeichnen* button next to it re-renders: if that
  clears a softness, the browser was holding on to an old picture.

The diagram places people by generation and then lays each family out as a tidy
tree: every unit is a person with their partners side by side, each unit is
given one primary parent so the graph becomes a forest, and parents are centred
over their children bottom up. Additional parent links are drawn but not used
for placement. An earlier barycentre sweep was dropped — its overlap pushes
compounded across generations and blew the full file up to 83000 pixels wide.

Placement runs in two phases. The centre's own line is laid out first as that
tidy tree. Every other family is then grown outwards from the marriage that
connects it, each unit taking the free slot in its row nearest to the relative
it hangs from. Before this, in-law families had no anchor at all and were simply
appended to the right-hand end of their generation: in the tree this was built
on, one married-in mother's parents sat 3182 pixels away from her and the
connecting line crossed the whole chart. They now sit 299 pixels away, directly
above her, and the full file shrank from 22914 to 14044 pixels wide.

Couples are then turned around where it helps. Husband and wife each hang under
their own parents, and if those parents sit the other way round the two descent
lines cross over the couple — which reads as if the pair were siblings rather
than a marriage. Swapping the two boxes costs nothing, since the unit keeps its
slot and its width, so the layout simply runs again afterwards and settles in
one pass. Across the full file that takes the crossings from 11 down to 1.

The one that stays is not a layout problem: it is the duplicated man
(#143 and #145), who is married to the same woman twice over, so his unit is a
threesome whose middle box cannot move. It disappears once the duplicate in the
source data is merged.

## Why the big views still cross, and the one that never does

Measured on the current build, centred on a person in the youngest generation
of a 326 person tree:

| View | People | Descent lines | Crossings | Width |
|---|---|---|---|---|
| Nahe Familie | 23 | 12 | **0** | 1 061 px |
| Ahnentafel | 117 | 59 | **0** | 5 900 px |
| Ganze Linie | 300 | 197 | 164 | 19 624 px |
| Alle | 326 | 207 | 174 | 23 094 px |

No boxes overlap in any of them.

A drawing without crossings needs a planar graph. A family chart laid out in
generation rows stops being planar as soon as it contains cycles, and a full
family file is full of them: both partners of every couple bring their own
ancestry, and in a rural region the same handful of lines married each other over
and over. Placing one couple well then forces another one badly. Crossing
minimisation in layered graphs is NP-hard even for two layers, so "just solve
it" is not on the table either.

The ancestors of a single person, on the other hand, are a genuine tree —
nobody descends from two children of the same couple — and a tree can always be
drawn flat without a single crossing. That is what the *Ahnentafel* view does,
and it is why it is the only one that can promise zero. Twelve generations,
117 people, no crossings, and a quarter of the width of the full view.

Block placement for the in-law families (below) was worth doing for the long
lines, but it barely touched the crossing count: 187 down to 174. The crossings
live in the main line itself, not in the families that married into it.

So the crossings that remain are made legible instead of removed:

- **Every sibling bar gets its own lane.** Bars are collected first, then sorted
  by their left edge and given the lowest lane still free at that x, so two
  families never share a horizontal line. Lanes are 11px apart in the gap under
  the parents' row, which is why `ROW_GAP` is 158.
- **A bar hops over any vertical line it has to cross**, the way a wiring diagram
  does — a 5px arc, so it is visible which of the two lines is continuous.
- **Two families' vertical lines never share an x.** When a child stands right
  under the middle of a foreign couple, its line would run down on top of that
  couple's line and its bar would end exactly where the other line comes down —
  a T that says the child is theirs, and a bar never hops at its own end. The
  child's line is moved 14px (`POST_GAP`) towards its own parents instead: it
  still lands on the box, the two lines run up in parallel, and the foreign line
  crosses the bar in the open, where it hops. Parent lines never move, they
  have to leave the couple from the middle.
- **Hovering a person lights up every line that belongs to them** and dims the
  rest. In the crowded ancestor rows this is the fastest way to follow a single
  connection; hovering a person in the middle generations lights 11 lines and
  marks 8 people.

One correctness note worth keeping: a blood relative is anyone descended from
one of the centre's ancestors. Walking parents and children together instead —
the obvious first idea — is wrong, because from a child one steps up into the
other parent, and then every in-law counts as blood. That bug made a whole
married-in family show up as the centre's own flesh and blood.

Note that the labels the page computes count side lines in grades, the way
German does and the report does: the first grade goes unsaid (*Cousine*,
*Neffe*), a cousin's child is a *Nichte 2. Grades*, a parent's cousin an
*Onkel 2. Grades*, and the child of a *Cousine 2. Grades* a *Neffe 3. Grades*.
Labels quoted from the report are still marked as to where they come from.

## Working on the program

Nothing needs building to change it.  The exe is only a frozen copy of the same
source, so the way round the build is to run the source:

```
python tools/edit_server.py
```

That is the program - same window, same data folder, same everything.  Two
switches help while working on it:

| | |
|---|---|
| `--port 8080` | a fixed port, so a browser left pointing at it survives a restart |
| `--kein-fenster` | serve without opening a window, and drive it from a browser of your own |

Where to change what:

| | |
|---|---|
| `tools/template.html` | the page - all of it. Style, diagram, editor, exporter. Save and reload the window; the render notices the file changed. |
| `tools/store.py` | the data folder and the trees in it |
| `tools/edits.py` | what a person is made of, and the two link rules |
| `tools/verknuepfung.py` | one person in several trees: what a link is, what travels, what is merged |
| `tools/edit_server.py` | the back end: routes, uploads, window lifetime |
| `tools/export.py`, `baum.py`, `gedcom.py` | going out and coming back in |
| `tools/build_site.py` | folding a tree into the page |
| `tools/extract_pdf.py`, `build_data.py`, `kinship.py` | the report pipeline, which is now only an import source |

When it works, freeze it again:

```
python tools/build_exe.py
```

The page is one file on purpose and stays that way: no bundler, no build step,
no dependencies to install for the front end.  It is plain HTML, CSS and
JavaScript, and a browser's own developer tools are the whole toolchain.

## Editing

`Stammbaum.exe` is the same page with a back end behind it.  Starting it opens
a window without an address bar, serves the page from `127.0.0.1`, and closes
the server again when the window is closed.  Building it:

```
pip install pyinstaller
python tools/build_exe.py
```

The exe is a program, not a bundle: it reads `Stammbaum.html` and `data/` out
of the folder it is sitting in, so the whole folder is what gets handed on and
what gets backed up.  Without the exe, `tools/Editor ohne exe starten.cmd` does
the same thing wherever Python is installed.

### How it knows when to stop

Not by waiting on the process Edge was started as.  That looks obvious and is
wrong: Edge hands the window over to a browser process of its own and the one
that was launched returns immediately, so the server shut down the moment the
window appeared and left an empty window behind.  A throwaway `--user-data-dir`
does not prevent it, and this only shows up when the real window path is run -
every headless test passes.

The page says it is still there instead: a ping every four seconds, and
`sendBeacon` as a last word while the window is being torn down.  Fifteen
seconds of silence ends the program.  That survives whatever the browser does
with its processes, and it also covers the window being closed from the taskbar
and the browser crashing.

### Why a back end at all

A page opened by double click runs from `file://` and is not allowed to write
anything.  Everything else follows from that: a local server, an app window, a
token in the URL so nothing else in the browser can post to it.

The page finds out that it may be edited from a single object that the server
injects into the head, `window.STAMMBAUM_EDIT`.  The file on disk is served
byte for byte as it lies — the copy for the family and the copy being edited
are the same file, and the read-only one never paints a single editing rule.

### Several trees, and only one import

Importing is something you do once.  A tree that arrives becomes a tree of its
own in the program's folder and is simply there afterwards; the heading in the
masthead is the switch between them.  That is what the arrangement is for:
your side, your wife's side, and whatever somebody sent you to look at, without
any of them having to be read in again.

    <the data folder>/
      einstellungen.json     which tree was open, and where each one lives
      SB_Rodenberg/
        baum.json            the people, the marriages, the heading
        fotos/               portraits, referenced by file name
        dokumente/<nr>/      scans belonging to that person
        sicherung/           the last twenty saves
        source/              the report this tree was built from
        data/                what the parser made of it
        Export/              finished pages, diagrams and books
        Stammbaum.html       the page for the family
        report.json          what to read, and who gathered it
      SB_Hemken/
        ...

Keeping each tree whole in one folder is what makes the rest simple: removing
one is moving a folder - into `_geloescht/`, because a family should not
disappear on a mis-click - and a portrait can never end up attached to somebody
in another family.

That was only half true until September 2026.  The trees sat under `baeume/`,
but the report, the parsed data, the exports and the finished page lay loose in
the data folder and were shared by all of them: a second tree overwrote the
first one's page, and `build.cmd` and the editor read from different piles.
Everything belonging to a tree now lives under that tree.  A data folder still
in the old shape is offered the move on start and carries it out on a click -
never on its own, because it moves a family's portraits and papers.

The folder name comes from the tree's name, umlauts spelled out, and is only a
folder name: renaming a tree changes what it is called, not where it lives.

### Two ways in, two ways out

| | |
|---|---|
| `.baum` | this program's own. One file with the tree, the portraits and, if allowed, the scans. Inside it is an ordinary ZIP, and a `LIES MICH.txt` says so - rename it, open it, and there is readable JSON and the family's photographs. A format nobody can open without the program that wrote it is not a way of keeping anything. |
| `.ged` | GEDCOM, how family trees have been passed between programs since the eighties. MyHeritage writes it, Ancestry writes it, Gramps and Family Tree Maker read it. |

GEDCOM support is what makes the program worth handing to somebody who already
has their family somewhere else - and what makes sure this family's work is not
trapped in here if the program is ever gone.  The load bearing part of 5.5.1 is
covered: names, sex, birth, christening, death and burial, occupation,
religion, residences, notes and portraits; families with marriage, divorce and
children.  Sources as records of their own, LDS ordinances and ANSEL are not -
but nothing unrecognised is dropped, it is kept verbatim under the person and
written out again.

Measured on the whole file: **326 people out and back in, nothing lost, no link
and no fact different.**  Two things that round trip found and that are worth
not undoing:

* **A name written is not a name assembled.**  `Knut Cordes` carries the given
  name `Knut, Dr.`, so rebuilding the name from its parts renamed him.  GEDCOM
  already answers this - the NAME value *is* the name as written, with the
  surname marked off by slashes, and GIVN and SURN carry the parts.
* **A couple of two women lost each other.**  GEDCOM 5.5.1 has one HUSB and one
  WIFE, so picking the role from the person's sex alone wrote WIFE twice and
  only the first survived reading back.  The slot is a place in a record, not a
  claim about anybody: where the sexes do not settle it, position does.

### Putting two families together

Import can also read a tree *into* the open one - which is the case where you
have your side and somebody brings theirs.  Everyone arrives with fresh
numbers and keeps their own connections; the two families stand next to each
other until somebody draws the marriage that links them, and then every
relationship label recomputes itself.

**Nothing is merged automatically.**  People who appear in both, by name and
year of birth, are listed and left alone.  Joining two people by name is how a
family file quietly acquires a wrong grandmother, and the two who married each
other know which two they are in a way no name matching does.

### Keeping them apart, and joined at one person

Importing puts two families into *one* file.  The other case is the common one
and wants the opposite: a wife's family should grow in **her own** tree, and
still be reachable from his.  She has to stand in both - he needs her to draw
his marriage, she needs herself to hang her parents off - so she is one person
carried by two files.  That is a **link**, and `tools/verknuepfung.py` is all
of it.

**The record is copied, not referenced.**  A tree has to survive alone: it goes
to relatives on a stick, it is backed up, it is opened in ten years.  A record
that only points into another file is empty the moment that file is missing,
and removing a tree from the program would then silently gut a second family.
So both files carry the whole person, and saving writes to every tree that has
her - `store.spiegeln`, straight after the tree in hand is safely on disk.
That order is deliberate: a second family's folder that has been renamed or
made read-only is reported, never allowed to cost the save somebody is watching.

What travels is the person; what stays is the tree.  Name, dates, places,
occupation, life stations go to every copy.  The number, the parents, the
spouses, the children, the portrait and the documents stay local - which is
exactly why the two trees can join her to different relatives without
contradicting each other.  Her parents are in her tree, his are in his, and
neither file has to know about the other's.

**Groups travel with her, whole or not at all.**  Four are hers: partner,
children, parents, siblings - offered in that order, because a partner and the
children are what make her placeable at all on the far side and the rest is
context.  Three more are the same question asked of her partner instead of her:
his children, his parents, his siblings - her parents-in-law, her brothers- and
sisters-in-law, her step-children.  That is the family she marries into, and it
is the family the second tree exists for; without it her own tree started with
her alone and every in-law had to be typed a second time by hand.

The married-in three stand in their own block and are **not ticked in advance**.
They are one step further out, and a second family should not travel because
nobody looked.  They also hang off a partner, so the partner is not optional:
ticking one of them ticks `Ehepartner` too, visibly, and unticking him drops
them again.  Without him his parents would arrive over there with no line to
anybody, because a link is only ever drawn when both ends travelled.
`verknuepfung.mit_ehepartner` enforces that on the server as well, so a direct
API call cannot get around it.

Half a set of siblings is a decision nobody remembers taking; three of four is
done by taking all four and removing one afterwards, which asks per tree what
should happen.  The dialog names the people by name before anything is written,
and it also says who the target tree **already has** under those names - asked
in both directions, because the second half is the one nobody thinks to check
until they see somebody twice.  Nothing is matched automatically, for the same
reason as above.  That preview is what somebody decides on, so it is not
allowed to lag: each tick asks the server again, the answers need not come back
in order, and only the newest one may write.

`link.via` is what keeps the two families apart afterwards.  It is set on
everybody who travelled *along with* somebody, empty on the person who was
linked herself.  So the wife is in her husband's "Alle" - she married in - and
her parents are not: they are one step further out, and the view stops at
married-in.  A step-parent's own child is on the near side of that line and
stays, which is the one case where the rule is not simply "one step".

A linked person can be taken out of a tree two ways, and deliberately not a
third.  **Verstecken** keeps the record and stops drawing it, in this tree
only - for a relative somebody no longer wants to see but does not want to
lose.  **Entfernen** asks which trees, ticks nothing in advance, and removes
her only from those; the tree in hand is marked but not pre-ticked, so the tick
is the confirmation.  What there is no button for is cutting the link and
leaving both records: that hands somebody two identical people who drift apart
from that day on, which is more work afterwards rather than less.

Two copies can disagree if a tree is edited outside the program.
`verknuepfung.zusammenfuehren` is the answer and it **merges rather than
picks**: lists - life stations, residences, notes - are unioned without asking,
because one person enters the marriage and another enters the job and both
belong to her.  Only single values that cannot both be true, two different
dates of birth, are reported as a conflict.

### Where the edits go

**Never into `data/tree.json`.**  `build_data.py` rewrites that file from the
PDF on every run and would take the handiwork with it.  Hand edits live in
`data/edits.json` and are folded on top afterwards — by the server while
editing, by `build_site.py` when the page for the family is written.  So a
newer report PDF can be read in at any time without losing a keystroke.

The overlay stores whole person records, not field-level patches: what the form
last showed is what is on disk.  Only people who were really changed are
written — a spouse who was merely looked at stays out, because a record in the
overlay outranks the report for good.

| | |
|---|---|
| `data/edits.json` | the overlay: changed and hand-added people |
| `data/photos/eigen_<id>_*.jpg` | portraits added by hand, kept apart from the ones the PDF gave up |
| `data/dokumente/<id>/` | scans belonging to that person |
| `data/dokumente/_geloescht/` | documents taken off a person — moved, never deleted |

Ids 1–326 belong to the report; they are the superscripts printed behind the
names.  Anything added by hand starts at **1001**, so re-reading a newer PDF
can never collide with a person typed in here.

### The two link rules

They are written twice — `tools/edits.py` for the file, the page's own
JavaScript for the live diagram — and the two must stay in step, the same way
`kinship.py` and the page's relationship maths do.

* **`parents` is the truth about descent, `children` is derived from it**, the
  same way `build_data.py` derives it from the report.  So "give this person a
  child" is stored as a parent link on the child, and cutting a link from
  either end really cuts it.  This is what makes the *Kinder* box in the form
  safe: it edits the child's parents, not a second list that could drift.
* **`spouses` is symmetric and cannot be derived**, so both records are written
  whenever a marriage is added or removed.

There is deliberately no "degree of relationship" field.  Every label in the
page — *Cousine 2. Grades*, *3 x Ur-Großvater* — is computed from parent and
marriage links for whichever person is the centre at that moment.  A degree
typed in by hand would be right for exactly one centre and wrong for the other
325, and it would silently break the check that compares 216 of the report's
own labels against the parsed graph.

### What a person can carry now

Everything the report gives up, plus the fields it has no idea about:
Rufname, Geburtsname, Titel, Konfession, Beerdigung, a list of **Wohnorte**
with years, a **Lebenslauf** of as many stations as wanted — each with a date,
a place and a sentence about what happened — **Kontakt** for the living, a
**portrait**, attached **documents**, and one free text field for everything
that has no box.

`--alles` aside, `build_site.py` leaves **contact details and documents out**
of the page it writes.  That page gets forwarded through a family; a telephone
number and the file name of a divorce certificate should not travel with it.

An e-mail address in the person sheet is a `mailto:` link, in the editor and in
any exported page that carries it; text that is not an address stays text.
**Optionen → Alle anschreiben** gathers the addresses of the living who are not
hidden in the open tree, one per address even when two people share it, lets
single people be unticked and opens one mail with all of them as **BCC** - the
yearly "anything new?" without handing everybody the others' addresses.  A
`mailto:` link is only passed on reliably up to about 2000 characters, so past
that the addresses go to the clipboard, separated by `;`, and the mail opens
without them.  "Adressen kopieren" does the same by hand for a mail program
that refuses the link.

### What a connection is called

A tie used to be a number in a list and nothing else.  Two people were in
`spouses` together, which said they belonged to each other but not whether they
had married; somebody was in `parents`, which said they were a parent but not
whether they had borne the child or come along later.  Both distinctions are
ordinary genealogy, both were being kept in people's heads, and the diagram
drew every couple with the double line that means a marriage whether it was one
or not.

Two maps carry it now — `spouse_kind` beside `spouses`, `parent_kind` beside
`parents` — and the lists themselves did not change, so a reader that knows
nothing about the new fields still sees every person and every connection.  See
[`FORMAT.md`](FORMAT.md), version 3.

Each is a dropdown to the right of the name in the form, one line per person so
that the roles line up down the page:

* **Ehe or Partnerschaft.** Written on both records, because being married is a
  fact about the pair.  A marriage keeps the double line; a partnership gets a
  single dashed one.
* **Elternteil, Vater, Mutter, Stiefvater, Stiefmutter.** Two facts hiding in
  one word: which sex the parent is, and whether they are a step-parent.  They
  are stored where each belongs — the sex on the parent, the step on the child —
  and **that is why choosing "Vater" here fills in the father's own sex field.**
  It was being typed twice, in two forms, and the two disagreed often enough to
  notice.

Both sexes are always in the list, not only the one already recorded.  Offering
half of it reads tidier and makes the field useless for the case it is most
needed in: a parent entered a minute ago with no sex at all.  What the recorded
sex decides is what stands selected.

Nothing here ever clears a sex.  "Elternteil" means nobody has said, which is
not the same as unsaying what was known.

### Where the sex is not known

It used to come out male.  `MF` chose between two words and the fallback was
the first one, so a granddaughter nobody had got round to ticking was called
"Enkel" — the program inventing a fact in the one place a family tree is read
for facts.

There is a third word now.  German has a real one most of the time — Elternteil,
Kind, Enkelkind, Geschwister — and where it does not, both are named:
"Onkel/Tante" says exactly what is known, which is that it is one of the two.

### The sheet stays open

`Speichern` saves and does nothing else.  It used to close the form as well, so
every save was also a navigation nobody asked for, and the way back was to find
the box in the diagram and click it again.  Filling a person in properly means
saving several times on the way.

Leaving is the ✕, the backdrop, or Escape — and each of them asks first, in the
page rather than through `confirm`.  `confirm` can only offer two answers, and
the two it offered were "lose the work" and "stay put"; the one somebody
standing in front of it actually wants, **save it and carry on**, was not among
them.  All three are there now, and the caller hands the dialog what to do once
it is answered.

The ✕ rides along at the top the way the save bar rides along at the bottom.  A
person's sheet is long enough to scroll, and getting out of one used to mean
scrolling all the way back up to find the way out.

A name in the form is a way through to that person: working down a family means
hopping between them, and the hop goes through the same question, so nothing is
left behind by it.

## The exporter

`Exportieren`, next to the manual button, writes the tree out for somebody
else.  It is a sheet of tick boxes rather than a button, because the question
is never only *what format* but *what may leave the house*.

**Centre:** asked first, *Mit* or *Ohne Mittelpunkt*.  It changes how the people
are shown, never which.  *Ohne* is sent as no centre at all: the diagram drops
the marked box, the relation tags (the line under the name stays empty), the
in-law tint and the family islands; the book drops its "Mittelpunkt" line; the
page loses the report's relation labels and `meta.root`; the file name carries
no person.  With no centre in the view the choice stands on *Ohne*.  The
diagram is read off the plane rather than redrawn without a centre, because
the layout depends on the centre and the screen must not move.

**Content:** the diagram of whichever view is open, the person book, or both -
both showing the same people, the ones on the stage right now.

**Format:** PDF, HTML, SVG, PNG — any combination.

**Fields:** ten groups.  Contact details, scanned documents and the report's
own prose start unticked.  What is not ticked is **cut out of the data** before
anything is written, not hidden with CSS: the exported page's `DATA` object
does not contain it.

Everything lands in `Export/`, named after the tree, the view, the centre (if
it is shown) and the date.

### The view is a filter, not a picture frame

The diagram was always right, because it arrives already drawn by the page.
The book and the HTML page are built on the server instead, and they used to be
built out of the whole tree no matter which view was open: a *Ganze Linie* of 23
people came out as a 99 page book of all 326, with people in it that had been
deliberately left off the stage.  The page now sends the ids it actually shows,
and `only()` in `export.py` cuts everybody else out before anything is written.

Cutting people out would leave references pointing at nobody, so the lists of
parents, spouses, children and event participants are cut down to the survivors
too, as are the marriages and the check report.  **No name appears in an export
that has no entry of its own** - which does come up: the parents of a
married-in partner sit one step outside *Ganze Linie*, so their names would
have shown in an `Eltern:` line belonging to nobody in the book.  The heading
counts are restated for the same reason; a page saying "326 Personen" above 23
entries is wrong in the first place anybody looks.

What cannot be filtered is prose.  A life story or a source note is a sentence
and names whoever it names, which is why those two groups - `notizen` and
`bericht` - start unticked, like the contact details do.  In fact only three
boxes start ticked - life dates, places and family - so that a file made in a
hurry carries the essentials and nothing more.

Contact details open into one tick per line - Telefon, Mobil, E-Mail,
Anschrift - none ticked in advance.  `trim()` keeps only the ticked lines of a
person's `contact` and drops the object entirely when nothing is left, so an
export that lets the e-mail address out has no telephone number in its data.

The two data formats are the exception and say so in the dialog: a `.baum` file
and a GEDCOM are for handing over *the tree*, so they stay complete and are
named without a view.

### The diagram is redrawn, not photographed

A picture of the screen would be a picture of the screen.  The page instead
walks its own laid-out plane and emits real SVG — one `rect` per box, the wires
copied over as paths, portraits as the same data URIs the page already holds.
So the drawing is vector: it opens on a phone, it opens in Inkscape, and it
goes to a print shop as a poster.

Two details that came out of the first print:

* **Names shrink rather than break off.**  On screen a name too long for its
  208px box is cut with an ellipsis, because a row of boxes has to keep one
  type size while scrolling.  On paper that is a lost surname, so the type
  steps down to 10.5px first.  Across the full file that takes the name font
  from 15.5px down to about 6pt at print scale, and nothing is truncated.
* **Everything is drawn in the light palette**, even when the screen is in
  Abendlicht.  This goes to paper and to other people.

### Page sizes

| | |
|---|---|
| the diagram | one page, as wide as the drawing, capped at 190 inch |
| the person book | A4, entries packed and never split across a page break |

*Alle* comes out as a single page of **483 × 53 cm** — a 4.8 metre poster with
all 326 people on it, every name in full.  The cap exists because PDF readers
stop opening pages somewhere past 200 inch.

Both sizes come out of **one** print run: Chromium understands named page
rules, so the poster page and the A4 pages can live in the same document.  The
first version printed two files and merged them with pymupdf, which worked but
froze a 42 MB library into the program for one function.  Asking for the two
halves as separate files is simply two runs.

The printing itself is done by Edge in headless mode: it is already required
for the program window, it renders the same CSS the page does, and it prints
without a dialog.  Better typography than anything worth hand rolling here.

The same thinking keeps Pillow out.  `build_site.py` uses it to shrink
oversized portraits, but the report's own photos are none of them wider than
300px, so the step never fires - what could fire it is a portrait added by hand
straight off a phone.  That one is therefore shrunk in the browser, to 600px,
before it is ever sent.  Nothing large is written, and the program stays at
7.6 MB instead of 25.5.

### What PNG cannot do

Browsers stop at **16 384 pixels** in either direction; past that the canvas
comes back blank rather than failing, which is worse than a refusal.  So the
PNG box is disabled for the views that are too big, and says by how much.

| View | Size | PNG |
|---|---|---|
| Nahe Familie | 1 767 × 1 158 | yes |
| Ahnentafel | ~6 000 × 2 000 | yes |
| Ganze Linie | ~19 700 × 2 500 | no — SVG instead |
| Alle | 23 647 × 2 580 | no — SVG instead |

## Layout of the two folders

There are two, and the split is the point: **the program is a repository, the
data is not.** Nothing under the first folder names a living person, so the
whole of it can be published; nothing under the second one ever leaves the
machine it is on.

```
<the program>/
├─ Stammbaum.exe             the editor - double-click; built, not committed
├─ build.cmd                 double-click: runs all three build steps
├─ README.md                 the front door
├─ CLAUDE.md                 how to work in here
├─ docs/DESIGN.md            this file
├─ datenordner.txt           where the data went - a setting, not committed
├─ tools/
│  ├─ extract_pdf.py         step 1
│  ├─ build_data.py          step 2
│  ├─ kinship.py             relationship maths, used to check the parsed graph
│  ├─ build_site.py          step 3 - folds the overlay in on the way
│  ├─ template.html          the page itself; the data is injected into it
│  ├─ edits.py               person records and the two link rules
│  ├─ store.py              the program's data folder and the trees in it
│  ├─ baum.py               the .baum file: packing, unpacking, merging
│  ├─ gedcom.py             GEDCOM in and out
│  ├─ export.py             the exporter: person and field filter, book, PDF
│  ├─ edit_server.py         the editing program - window plus local back end
│  ├─ build_exe.py           freezes that into Stammbaum.exe
│  └─ Editor ohne exe starten.cmd   the same thing where Python is installed
└─ (no data of any kind)

<the data folder>/           chosen by whoever runs the program - see store.py
├─ einstellungen.json        which tree was open, where each one lives, program options
└─ SB_<name>/                one folder per tree, everything of it inside
   ├─ baum.json              the people, the marriages, the heading
   ├─ Stammbaum.html         the deliverable - one file, hand this out
   ├─ report.json            what to read, and who gathered it
   ├─ Namensliste.txt        every person with their number, one per line
   ├─ fotos/                 portraits, referenced by file name
   ├─ dokumente/<id>/        scans belonging to a person
   ├─ sicherung/             the last saves, oldest thrown away
   ├─ source/                the report PDF, kept so the build stays repeatable
   ├─ Export/                finished pages, diagrams and books
   └─ data/
      ├─ tree.json           the parsed report - written by the pipeline only
      ├─ edits.json          the overlay of the arrangement before this one
      ├─ validation-report.txt  what did not add up
      ├─ photos/             the portraits cut out of the report
      └─ raw/                intermediate text from the PDF, handy for grepping
```

`baum.json` is the tree as it is kept; `data/tree.json` is what the report said
when it was last read.  The page is built from the former and only from the
latter when asked - `build_site.py --aus-bericht`, which is what `build.cmd`
passes, being the chain out of the PDF.

### Where an option is kept

Never in the editor window's browser storage.  The program listens on a new
port every start, and the browser files what it remembers under the port, so
anything kept there was gone by the next start.

| Kind | Examples | Kept in |
|---|---|---|
| **the program's** - holds whichever tree is open | Tageslicht/Abendlicht (`theme`), `stationen_auto`, `stufen`, `mitnehmen`, `offen` | `einstellungen.json`, via `store.remember()` |
| **one tree's** - travels when the tree is handed on | "Das bin ich" (`meta.root`), `meta.mitnehmen` | `baum.json` of that tree |
| **one window's** - gone when it closes | jump-back trail, message after a reload | `sessionStorage` |

The page handed around has no program behind it, so there the reader's browser
is the only place left: Tageslicht/Abendlicht and "Das bin ich" go into
`localStorage`, and the copy ignores `meta.root` on purpose so nobody inherits
somebody else's middle.  A light chosen in a browser before the program kept
it is taken over once, the first time the program has none.  The saved light
is set in the head, before anything is drawn; print and export stay light
whatever it is.

### Why they are apart

Because a `.gitignore` is a rule, and a rule holds only while it is correct.
This program's own history is the argument: real names reached a published
repository not through the data but through **examples in comments**, written
while working on the code, with the data sitting in the same folder and the
ignore list looking fine.

Data that is not in the folder cannot be committed from it, whatever else goes
wrong. The ignore list is the second line, and it names what data *is* rather
than only where it sits: a portrait dropped in here to try something is caught
by `*.jpg`, not by a folder rule.

There was a pre-commit hook doing the same job for a while. It went, because a
hook lives in `.git/hooks`, which is not part of a repository - every fresh
clone starts without it, and it is missing precisely when somebody unfamiliar
is looking around. The ignore list arrives with the clone.

Neither reads the code for names, and that is worth saying plainly: both of the
leaks that actually happened came through comments, and no rule about where
files live would have caught either.

A third one happened in September 2026, and it came in a way neither line
covers: through a *conversation*.  Names spoken while describing the problem -
whose family, which wife, which two trees - were carried straight into the
examples of a new test file and into a pull request, where they were public.
Nothing on this list was ever going to see that.

So there is now a check that reads the code: `tools/test_keine_namen.py`.  It
takes the names out of the data folder - the one place they legitimately live -
and fails if any of them appears anywhere in this repository.  Three things
about it are deliberate:

* **It gets the names from outside.** A list of forbidden names inside the
  repository would itself be the leak.  It reads `baum.json`, and only the
  fields that really are a name.  The readable `Namensliste.txt` was the
  obvious second source and is the wrong one: it has a heading and prose, and
  taking every word from it flagged 1502 lines including `.gitignore` - a check
  that cries wolf is worse than none.
* **It never prints what it found.** A failure names the file and the line.
  Saying which name matched would put it in a build log, which is the thing
  being prevented.
* **It is a test, not a hook.** That is the whole point - a hook lives in
  `.git/hooks` and no clone brings it along, which is why the last one went.
  A test arrives with the clone and runs with `python -m unittest discover -s tools`.

On any machine without a data folder it skips and says so, rather than passing
quietly: it cannot check what it cannot see. Which also means it only protects
the machine the family is actually on - so it belongs in the run before a push,
not in a build server that has nothing to compare against.

Plus `Export/`, which the exporter writes into.  Neither that nor
`Stammbaum.exe` is committed - the exe is 7.6 MB of frozen Python and rebuilds
in a minute, and everything in `Export/` is derived from the two files that
matter.  `data/edits.json` is committed, because it is the handiwork.

`data/raw/marked.txt` is the readable version of the PDF with the superscript
ids kept as `{12}` markers. Grep it when a parsing question comes up.

## Next, when it is picked up again

Two of these are about the data rather than the program, and are kept out of
this repository along with it:

- **People born after the report was printed.** The editor exists for exactly
  this; the dates have to come from the family.
- **Merging a duplicated branch.** Cleanest upstream, in MyHeritage, followed by
  a fresh PDF and `build.cmd` — the overlay survives that, which is the whole
  point of it.
- **Stub notes in an outside note system**, if wanted — linking here rather than
  holding a second copy of the data.
